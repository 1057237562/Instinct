# Instinct 指令理解定向调优计划

本计划只规定下一轮实验，不启动训练、不覆盖当前模型。已确认历史：`pretrain_codespecialist.jsonl` 两轮预训练，`sft_t2t_mini.jsonl` 一轮 SFT。当前候选起点为 `out/instinct-v1-0914.pth`，完整配置取 `checkpoints/full_sft_20260914_200306_768.json`，保留权重及数据指纹。

## 目标与判断

优先采用继续全参数 SFT，先不重新预训练，也不直接启动 GRPO。当前有明确的指令/答案对应错误、条件遗漏、无依据补全和重复模板，但没有受控实验证明某个单一原因。目标是提高一次生成的指令正确率，不追求单靠增加采样提高 pass@100。

现有 `dataset/quality_python_sft/continue_sft_reviewed_train.jsonl` 有 14802 条、约 673 万渲染 tokens，适合代码/数学补强；其中约 70% 是代码 tokens，不能替代专门的指令理解课程。下面新增指令数据仍待制作，不把计划中的样本数写成已完成。

## 阶段 0：先建立可信的基线

1. 修复 HumanEval 的代码块选择、保护题目辅助函数，并用已保存答案重评。GSM8K 同时报严格格式率与明确终答的数值正确率；无法可靠提取时不随便取末尾数字。
2. 固定聊天模板、greedy、生成上限和后处理；选相同小批题比较 thinking 开/关、batch 1/较大 batch、KV fp32/现有低精度配置，排除设置导致的退化。各条件结果独立记录。
3. 检查实际 SFT 标签：用户与 system tokens 是否被屏蔽、assistant 内容和 EOS 是否有监督、工具调用字段是否完整、reasoning_content 是否被意外加入无效长推理。用实际 tokenizer/render 检查，不只读取 JSON。
4. 加载前比对参数键和 tensor shape。现有 trainer 加载路径含 strict=False，不能仅凭启动成功认定完全加载；模型必须匹配 20 层完整配置。
5. 保存初始权重哈希、完整 args、训练/验证文件 SHA-256，固定评估题列表。

产物：一份冻结基线报告。未完成前，不用现有原始 HumanEval 分数给训练收益定量下结论。

## 阶段 1：新增可验证的指令数据

建议先制作约 8000–12000 条独立任务，按下面类型覆盖。数量为制作目标，重点是准确、独立和可检查，不机械换名字扩大规模。

| 类型 | 数据设计 | 对应错误 |
| --- | --- | --- |
| 输出契约 | 只输出数字/JSON/一个代码块；固定字段、指定数量、给定语言 | GSM8K 缺少终答；要求英文却中文；多个代码块 |
| 相似规格对照 | 相同输入分别做不同操作；最小改动指令导致不同正确答案 | 去重与移除全部重复混淆；忽略个位乘法等限定 |
| 上下文提取与转换 | 只依据给定短文本提取、分类、排序、单位转换，禁止补入无来源字段 | 虚构缺失内容；混淆实体与数量 |
| 多条件执行 | 从一个条件逐步增加到两个、三个条件，训练合取、例外和顺序 | 只执行日期/文件名的一条规则 |
| 缺信息澄清 | 输入真的缺少必要正文或数据时，简短请求补充；信息齐全时直接完成 | 缺少正文仍编造；有完整题目却反问或拒绝 |
| 多轮最小修改 | 只修改用户指定的一个字段/一处代码，其余保持一致 | 修改范围失控；忽略后续修正 |

示例：同一输入 `[4,7,7,9]`，指令 A“保留每个值的第一次出现”对应 `[4,7,9]`；指令 B“只保留恰好出现一次的值”对应 `[4,9]`。两者都作为正确示范，不将错误回答作为普通 assistant 目标。

制作要求：

- 每条明确成功条件；能用解析器、函数执行或参考变换验证的直接验证，不能自动判定的分来源人工抽样。
- 单条优先一两项约束；短回答为主，不强制长 CoT。计算题可给简短正确算式链。
- 约一半中英文任务，另设少量“指令语言与要求的回答语言不同”的测试。该比例是初始设计，按实际使用语言调整。
- 不把 `tools="[]"` 的记录当作真实工具调用。工具样本需有真实定义、参数和调用结果对应关系。
- 按任务族/模板和原始问题分组切分，验证使用未见表述与组合，防止只记格式模板。
- HumanEval、GSM8K test 和 IFEval 测试题不作为训练来源；用自建独立内容实现同类可检查要求。

## 阶段 2：小规模对照 SFT

建议新指令混合按渲染 token 配置：

| 成分 | 初始比例 |
| --- | ---: |
| 输出契约、对照规格、上下文转换等显式指令 | 45% |
| 修订后的 Python 短函数 | 25% |
| 简短基础数学解答 | 15% |
| 缺信息澄清与多轮最小修改 | 5% |
| 已清理的普通对话/真实工具回放 | 10% |

该比例是待验证起点，不是最优配方。BigCode 待审部分及原 SFT 大量未清理回放继续不纳入。

先做两个相同训练 token 预算的实验，均从同一个当前 SFT 权重独立开始：

- A：现有人工抽样修订的代码/数学集合，作为对照。
- B：新增显式指令混合，作为主候选。

先各训练约 100 万非 padding 渲染 tokens 做小试，记录 assistant 监督 tokens 数；B 有稳定收益后才扩至约 300–600 万。不要按“行数相同”误认为训练量相同。这个量级是预算建议，不是需要重复整个 90 万条旧 SFT 集。

参数起点（须以显存和验证结果调整）：

| 参数 | 建议 |
| --- | --- |
| 起始权重 | `out/instinct-v1-0914.pth`，加载现有权重但新建 optimizer；不是从旧训练的优化器位置 resume |
| 调优方式 | 全参数 SFT；当前模型规模先保持方案简单 |
| optimizer | AdamW，沿用项目实现 |
| learning_rate | 主试 1e-5；若出现退化，再从同一基线重试 5e-6 |
| 参数/计算精度 | param_dtype=fp32，dtype=bfloat16，避免小学习率直接更新半精度参数的量化影响 |
| max_seq_len / bucket 上限 | 4096；整条超长样本丢弃，不截断指令或答案 |
| batch / accumulation | 从 batch 4、accumulation 8 起，按实测显存调整；启用 packing 时实际 token 数另记 |
| grad_clip | 1.0 |
| 调度 | 沿用项目现有余弦；当前 get_lr 不能假装有未实现的 warmup 配置 |
| epochs | 第一轮只做 1 轮等效曝光；是否继续由验证决定 |
| 编译与额外 FP8 | 小试先用确定的基线配置；确认正确性再独立做性能优化 |

现有脚本没有通用 token-budget 停止、自动验证与早停接口。执行前应制作满足预算的独立数据切片，或增加经过检查的预算停止逻辑。保存里程碑时需保留不可覆盖的副本：当前周期保存会更新同名权重，不能据此假设已有完整 checkpoint 历史。第一轮至少比较起点、中段和结束三个快照。

## 阶段 3：如何判定有效

新建约 600 道独立验证题，六类各约 100 道，并保留当前 841 条修订验证数据检查代码/数学能力。600 题分开发用集合与最终封存集合；开发过程中不针对封存题反复改数据。

核心指标分开统计：

1. **单约束满足率**：语言、格式、字段、数量等分别统计。
2. **整题全部约束满足率**：必须同时完成内容要求和所有格式条件。
3. **相似规格对照双正确率**：一对 A/B 两个任务都做对才算通过。
4. **内容正确率**：代码功能测试、数学数值、提取字段准确性，不与格式混为一谈。
5. **澄清选择**：缺信息时是否正确澄清；信息完整时是否不必要地反问。
6. **重复率与耗尽生成预算比例**：冻结检测规则，比较同一评估集合。
7. **保留能力**：中英文日常对话和真实工具参数正确率。

暂定验收门槛，建立基线后可调整一次并冻结：

- 单纯格式/语言任务满足率达到 90% 左右；这是目标，不是保证。
- 未见模板的全部约束满足率比基线提升至少 15 个百分点；用相同题逐题比较，并报告样本数与不确定性。
- 重复率明显降低，争取不高于 5%。
- 代码/数学内容正确率和普通对话指标不出现超过约 3 个百分点的退化；小样本波动先复核，不能机械早停。

若只改善 `####` 或 JSON 格式、数学与代码功能仍不变，只能叫“格式遵循改善”。若训练 loss 降但未见模板的双正确率不升，优先查模板记忆、标签或数据冲突，不继续增加轮数。

## 后续分支

- 显式指令 SFT 有效且保留能力稳定：扩展条件组合和多轮任务，再做一轮小范围强化。
- 格式改善，条件理解仍弱：增加最小差异对照、否定条件、例外和反例边界，审查答案是否真的遵循全部规格。
- 普通能力下降：降低 LR/减少训练量，检查回放质量，再适度提高回放；不直接重新训练全部旧语料。
- 经多次受控 SFT 后仍普遍缺少基础运算和代码补全能力：再评估领域继续预训练，并随后重新 SFT，而非现在从头预训练。
- 模型已经能稳定产生部分正确候选，且奖励器通过审计后，再考虑基于可验证约束和功能测试的 RL。现有 GRPO 的通用文本奖励不能直接当作代码/数学正确性奖励。

## 依据与限制

[IFEval](https://arxiv.org/abs/2311.07911) 的可验证指令评估方法适合设计格式/约束检查；这里的小型自建集合不是官方 IFEval 分数。[InstructGPT](https://arxiv.org/abs/2203.02155) 使用示范 SFT 后再进行奖励优化，支持分阶段思路，但它不能证明上述比例和超参数对当前模型最优。

本项目证据还包括 `eval/gsm8k_20260915_weakness_report.md`、`eval/humaneval_pass100_20260915_investigation.md`、`dataset/quality_python_sft/manual_review.md`。数据许可继承原来源：包含 KodCode 的方案具有非商业限制。所有阈值、预算和比例均是建议实验设计，尚未执行或验证效果。
