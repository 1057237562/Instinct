# 统一评测 WebUI

包含代码块的段落使用 Streamlit 原生 Markdown 渲染，保留语法高亮及代码块复制按钮，流式未闭合代码块和 think 区域内的代码也适用。普通文字继续使用轻量 HTML 动画；代码不插入逐字动画标签，展示刷新仍受统一限频控制。

Think 区域只在收到代码块外的显式 `<think>` 起始标签后显示；打开思考开关、空输出或单独的 `</think>` 均不会创建思考区域。

CUDA 原生推理默认使用 `optimize_inference(..., 'auto')`：融合 RMSNorm / SwiGLU，并为单条、无填充的生成使用静态 KV Cache 和 CUDA Graph。Eval CLI、ToolCall 和 `batch_size=1` 的评测会在模型加载时预热这条快路径；首题不再承担图捕获开销。`full` 还会编译 Transformer 主干，但加载和首次实际提示可能花较长时间编译。批量或带填充的生成仍走普通解码；其总 tokens/s 是整个批次的吞吐，不能当作单条回答的 tokens/s。Windows 必须在启动前启用 `PYTHONUTF8=1`，Eval WebUI 启动子进程时会设置。修改代码只影响新启动的评测任务，正在运行的任务不会自动更新。

单条生成的静态 KV Cache 从较小容量开始，回答实际变长时才扩容，最大生成长度保持不变。原生 MoE 的多条批量生成若配置为 FP8 KV Cache，评测进程会先按批量大小和最大生成长度估算 BF16/FP16 缓存占用；显存余量足够时暂时使用模型精度，避免每步对增长的整段缓存反量化、再量化，批次结束后恢复原配置。余量不足时继续用 FP8。日志中的 `kv_cache_dtype` 标明本批实际精度。精度变化可能导致采样结果不同；需要与旧结果严格对照时，应固定环境并从空答案文件重跑。训练路径和 checkpoint 参数名不变。

聊天展示按块解析 Markdown，未闭合的 think 区域立即展开。展示层合并已到达的文本块，常规刷新上限 10Hz，长回答逐步降低到约 3.3Hz；结束时强制刷新，确保尾部完整。动画在 Markdown 解析后的文字节点上执行，每帧最多 64 个动画节点，超过 5 万字符停止逐字动画。解析结果使用有界缓存，避免反复解析上一帧；这些刷新策略不改变模型的 16-token 回传设置。

HumanEval 选择「生成并评分」时，默认一边生成一边评分，无需新增配置。日志和任务区显示已送评、已评分与等待数量。最终 pass@K 和压缩分析在所有测试结束后生成。LiveCodeBench 的官方完整文件入口仍在生成全部答案后评分。

原生模型生成默认每 16 个 token 回传并检查 EOS，聊天页面用浏览器 CSS 动画展开新文本；末尾不足 16 个会立即刷新。自回归计算仍逐 token 执行，这项优化减少的是 CPU/GPU 同步和界面更新。EOS 后最多额外执行 15 个被屏蔽的步骤，输出会截回真实结束位置。首段显示需要等待首块生成。返回 KV 缓存的底层调用保持逐 token 检查以保证缓存位置精确；普通聊天和评测使用 16-token 分块。

模型默认从 `out/*.pth` 下拉选择，按修改时间从新到旧排列。优先读取权重旁同名 JSON，再查找 `checkpoints/<权重名>.json`，自动恢复层数、hidden_size、注意力头、主干、残差、MoE 等完整结构。没有同名配置的旧权重（例如复制得到的 `best.pth`）需在「模型高级设置」指定原训练配置，不会猜测结构或使用其他运行的最新配置。`model` 目录只用于 tokenizer，不是权重来源。Transformers 模型和 LoRA 放在模型高级设置中。

主界面只保留模型、运行方式、K 和 Batch size 等常用项。每题样本数自动设为最大的 K；单样本使用贪心生成，多样本使用 temperature=0.8。设备由运行脚本检测 CUDA/CPU；评分并发按 CPU 数量取最多 4，随机种子固定 42，Top-p 固定 0.95。新任务答案路径自动带时间戳，LiveCodeBench 仓库自动查找项目内或相邻目录。数据来源、生成长度、续跑、评分超时等放在「评测高级设置」。

常用参数使用下拉预设，路径下拉会发现本地模型、权重、数据及评分结果。下拉列表可搜索；没有需要的选项时选择「自定义…」再输入。LiveCodeBench 日期范围使用日历选择。

## 计算 pass@K

HumanEval 和 LiveCodeBench 都可以选择 `pass@K`（例如 `1,5,10`），选择「生成并评分」完成答案生成、功能测试和指标计算。样本数和采样温度自动联动，也可在高级设置覆盖。已有答案选择「仅评分」。结果区显示百分比并可下载指标 JSON。

已完成评分时，切换「计算 pass@K」标签，填入 HumanEval 的 `*_results.jsonl` 或 LiveCodeBench 的 `*_codegeneration_output_eval_all.json`，即可计算其他 K，无需重新生成或测试。也可以运行 `python eval_pass_k.py --results eval/humaneval_samples.jsonl_results.jsonl --k 1 5 10 --output eval/pass_k_metrics.json`。

采用无偏估计 `1 - C(n-c,k)/C(n,k)`，其中 n 是每题样本数、c 是通过全部测试的样本数，再对题目取均值。只对每题都至少有 K 个样本的 K 报告指标，样本不足会明确提示。离线计算仅覆盖输入结果文件中的题目，不自动代表完整评测集。普通推理与 ToolCall 没有逐样本正确性标签，不能据其对话日志计算 pass@K。

HumanEval / LiveCodeBench 的「生成 Batch size」默认为 4，控制同时生成的答案数，支持跨题目和同题多个样本。可尝试 4、8、16，显存不足时减小。它与「每题样本数」及「评分并发数」独立：每题样本数决定 pass@k 采样数，评分并发数控制 CPU 测试并发。普通推理和 ToolCall 仍按原脚本逐用例运行。

普通 Transformer 对不同长度输入左侧补齐；原生 Linear 主干仅将相同输入长度的任务组批，避免补齐 token 污染循环状态，因此实际批次可能小于设置值。CLI 分别使用 `--batch_size 8`（HumanEval）和 `--lcb_batch_size 8`（LiveCodeBench），默认仍为 1。

批处理会复用同题分词结果，并按输入长度排序以减少补齐；每批统一将输出传回 CPU。原生模型的生成只投影最后一个位置的词表 logits；启用 flash attention 时，单 token 解码也使用融合注意力。日志中的 `[Eval batch ...]` 显示实际批次、补齐比例、生成 tokens/s 和耗时。判断优化效果应比较同模型、同配置的 tokens/s，而非仅看 GPU 利用率；CPU 功能测试阶段不会持续使用 GPU。运行中的进程不会自动载入代码修改，新任务才会使用新逻辑。

采样随机种子按批次设置，改变 batch size 或从部分结果恢复可能改变后续采样答案；已保存答案仍会保留。严格复现实验时固定批次大小，并从空输出文件完整运行。

仓库根目录执行：

```bash
python -m streamlit run scripts/eval_webui.py --server.address 127.0.0.1 --server.port 8503
```

Windows 可双击 `start_eval_webui.bat`，浏览器打开 http://localhost:8503。使用现有 requirements.txt 中的 Streamlit、psutil，无需额外安装 UI 依赖。

支持以下入口：

| 类型 | 功能 | 输出 |
| --- | --- | --- |
| HumanEval | 仅生成、仅评分、生成并评分，pass@k、本地数据、续跑 | 答案 JSONL、逐样本结果、指标 JSON |
| GSM8K | 官方 test 集，批量数学推理、数值判分、accuracy / pass@K | 答案、抽取值/参考值、压缩失败分析 |
| LiveCodeBench | 数据版本、日期范围、采样、续跑、官方评分 | 答案 JSON、官方 evaluator 结果与日志 |
| 推理自动测试 | eval_llm.py 内置 8 个问题 | 对话和生成速度日志 |
| ToolCall | eval_toolcall.py 本地模型内置用例 | 工具调用与回复日志，无准确率 |

在「配置评测」选择评测类型与模型。所有路径相对于仓库根目录，ToolCall 与其他入口共用完整模型配置加载逻辑。仅评分不会加载模型。可展开查看实际启动命令，点击「开始评测」后在「任务与结果」查看每两秒刷新的日志，也可停止整个任务进程树。

任务配置、日志和退出状态保存在 `eval/runs/<时间戳>_<ID>/`。刷新浏览器后可重新查看当前任务，同一 WebUI 服务只允许一个运行任务。停止 WebUI 服务前请先停止评测；服务重启后不会重新接管旧进程。历史记录若仍显示 running，仅代表最后保存的状态。

点击「刷新历史与结果」查看或下载最新结果。日志和配置按任务独立保存；答案及评分文件保留原脚本的输出位置，历史界面按该路径读取。需要保留多次评测时使用不同的答案路径。已有答案默认拒绝覆盖，可选择续跑，且必须保持模型、数据与生成配置一致。

HumanEval 的 pass@k 仅在每题至少有 k 个样本时计算；多样本需要 temperature > 0。LiveCodeBench 评分须安装官方 evaluator，并使用完整匹配的数据版本和日期范围（limit = 0）。评分会执行生成代码，应在隔离环境运行。
